# AWS customer IDE pod: first safe deployment gate

**Status: not deployed.** This directory defines a separate `coder-customers` Kubernetes namespace, one Deployment and one 10 GiB PVC per workspace in `customer-template/main.tf`, restricted namespace policy, scoped provisioner RBAC, and a read-only diagnostic. None of these files creates an AWS cluster or a customer pod just by being merged. Do **not** alter `wonderingtribe/production` or its template.

## Find the actual AWS cluster without terminal work

After review and merge, open GitHub **Actions → AWS customer pod preflight (read only) → Run workflow** on `Master`. It uses the *existing* `AWS_FALLBACK_HOST`, `AWS_FALLBACK_USER`, `AWS_FALLBACK_SSH_KEY` and pinned `AWS_FALLBACK_KNOWN_HOSTS` from the manual AWS web deployment. Set the **verified** `AWS_CODER_KUBE_CONTEXT` repository variable to the precise `kubectl config current-context` on that AWS host. This only makes sense if that host has trusted Kubernetes credentials for the intended AWS workspace cluster. Do not change the existing web deployment host to point at a different machine just to make this workflow pass.

The preflight reads cluster context, nodes, customer namespace quota/policies, RBAC, pod admission and StorageClass; it refuses a different or absent Kubernetes context. It checks that the customer service account cannot read Kubernetes secrets or operator resources. It does not install Kubernetes, apply manifests, mint credentials, create a workspace or change DNS. A failed check is a diagnosis, **not** permission to enable the customer rollout flags. If the AWS VM only runs Docker, a real AWS Kubernetes cluster (or independently planned k3s setup) and a correctly connected Coder provisioner are still missing. If the Coder control plane lives outside AWS, an AWS provisioner can target this workspace cluster without copying the operator workspace or requiring a `coder` namespace in AWS.

## Before installing namespace resources or creating a test pod

1. Confirm AWS cluster identity and version, node CPU/RAM availability, disk costs and an actual default storage class. Confirm the cluster CNI enforces `NetworkPolicy`; merely listing the policies proves nothing about enforcement. Review DNS and Coder agent outbound HTTPS against the real network.
2. Review `customer-isolation.yaml` and `customer-provisioner-rbac.yaml` with the cluster administrator. Only apply to `coder-customers`, never `coder`. The customer provisioner service account is **not wired to a running provisioner** by the manifest: a distinct, trusted Coder provisioner must actually use that identity. Do not bind the existing broad operator account to it. If your Coder edition does not support a separate external provisioner, design and verify an equivalent dedicated, namespace-limited provisioning arrangement before continuing.
3. Build and vulnerability-scan Linux/Node images with `code-server` already installed. Supply immutable image digests for **both** template variables; ensure non-root startup works with a read-only root filesystem and a writable PVC. Publish `customer-template/` as a **new** template without replacing operator templates. Verify the pinned active template version, storage binding, Coder agent readiness and wildcard app TLS.
4. Enable and verify two **different** Supabase-to-Coder OIDC user sessions and distinct Coder UUIDs. Exercise cross-user negative tests for Coder API, direct IDE URL, terminal, preview and PVC; inspect actual pod owner IDs and ensure the agent token never reaches the browser. The customer runner should create only through `/api/v2/users/{customer-id}/workspaces`.
5. Deploy and verify usage metering and a **separate enforced hard-stop** that still prevents running and direct-Coder restarting when the website, CronJob, database or API is unavailable. Define per-account compute allowance including delete/recreate before enabling billing or customer creation; see issue #553. The one-minute controller, TTL and namespace quota alone do not enforce that rule.

Only after the above live checks may the operator set the narrowly scoped customer verification switches. Start with **one paid test customer**, observe its unique pod and PVC and stop its compute after the test. The user-facing `Open my private IDE` link is Coder's own authenticated workspace page, not a new in-site IDE gateway.
