# Coder pod cost safeguards (review and deploy manually)

**Not active merely because this branch is merged.** Keep `CODER_WORKSPACE_CREATION_ENABLED` unset/false until the actual Coder cluster, origin certificate, billing database and Kubernetes policies have been verified. No migrations or Kubernetes resources have been applied by this PR. Do not enable billable operations if the provider has no acceptable budget/cap.

## New website behavior

- Only Stripe-backed active/trialing Pro/Team users can allocate a Coder workspace; Free cannot. Pro has **one allocated workspace**, Team **five**. Stopping or restarting the same workspace does not debit a monthly launch. A stopped workspace retains its 10 GiB PVC and still occupies a slot. Deleting it releases the slot **only after** Coder reports HTTP 404 for the exact workspace ID. Users can manage their own slots at `/wonderspace/workspaces`.
- Database function `reserve_coder_workspace_slot` serializes each user's concurrent creates with an advisory lock. The global unreleased-name uniqueness guard prevents collisions while Coder is configured with one shared owner. If Coder creation times out, the slot is deliberately retained, since Coder might have created a real pod. Staff must inspect Coder and reconcile it; do not delete the row just to make the UI work.
- The website allows at most 2 CPU / 4 GiB memory / 10 GiB persistent volume, with `ttl_ms = 1 hour` requested on creation. It denies creation unless both `BILLABLE_OPERATIONS_ENABLED=true` and `CODER_WORKSPACE_CREATION_ENABLED=true`. No end-user request can change the disk or TTL.
- The Terraform `cost-guard.tf` file in **both** Coder templates rejects a workspace created outside `coder-workspaces`, over those CPU/RAM limits, or with a disk size other than 10 GiB. This covers workspace starts through Coder UI/CLI **after the guarded template version is actually published**.
- The Kubernetes manifest limits the *entire* dedicated namespace to five workspace pods and five PVCs, 50 GiB total requested persistent storage, and bounded CPU/RAM. This is deliberately a small GLOBAL initial capacity, not five pods per customer. It does not cap the Coder control-plane server, its own database, existing pods in other namespaces, network egress, provider metering, or orphaned volumes.

## Deploy sequence, in order

1. Identify the actual Coder server and Kubernetes cluster: `coder config` or `coder list`, `kubectl config current-context`, and `kubectl get pods,pvc -A -l com.coder.resource=true`. The currently configured site Coder URL previously timed out and its public hostname returned HTTP 526. Repair the correct origin certificate and private server-to-Coder routing before relying on any launch or deletion call. Never paste session tokens into a ticket.
2. Export/back up workspace metadata and inspect existing pods and PVCs. The new `coder_workspace_slots` table starts empty and **does not automatically import preexisting Coder workspaces**. Reconcile existing owner/name/ID/user assignments before enabling customer creation. In particular, `CODER_WORKSPACE_OWNER=me` makes a shared Coder owner: verify tenant isolation and access-control behavior or migrate to per-user Coder identities before selling multi-tenant IDEs.
3. Test `supabase/migrations/202609202100_coder_workspace_slots.sql` in a NONPRODUCTION database with the actual target schema and authenticated users. Confirm anon/authenticated cannot read or execute it. Verify two simultaneous reservations with Pro limit 1 yield only one slot; a second username cannot claim the same active name. Apply it to the verified production Supabase project only after approval and rollback planning. Existing `reserve_billable_units` migration must also be validated separately for AI.
4. Apply `deploy/k8s/coder-workspace-cost-guard.yaml` on the **actual** cluster only after inspecting available nodes, StorageClass and control-plane namespace. It creates a new `coder-workspaces` namespace; it does NOT impose quotas on the existing `coder` control plane. Check: `kubectl get resourcequota,limitrange -n coder-workspaces`, `kubectl auth can-i create deployments -n coder-workspaces --as=system:serviceaccount:coder:coder-workspace-provisioner` and the same for PVCs. Scope the Coder provisioner to this namespace, removing broad old permissions only after confirming its other duties.
5. In Coder, publish the two guarded template directories with `coder templates push <ACTUAL_TEMPLATE_NAME> --directory infra/coder/template --variable namespace=coder-workspaces` and the equivalent `infra/coder/templates/playcanvas-3d`. Use the REAL template name returned by `coder templates list`. Preserve existing template variables and parameters. Test a workspace creation with CPU 4, memory 8, disk 50 and namespace `coder`; each MUST be denied. The current template's default disk/namespace settings are legacy; the website supplies disk 10, but Coder UI/CLI direct launches must explicitly use the guarded values until template defaults are updated and tested.
6. Set default autostop to 1 hour in Coder template scheduling (for example, `coder templates edit --default-ttl 1h <ACTUAL_TEMPLATE_NAME>`). In Coder admin template scheduling, prevent users from disabling or extending autostop beyond the operator-approved cap. Verify an idle test workspace actually STOPS, that stopping removes its running pod but preserves the PVC, and that a failed provision is cleaned up without deleting user data. The old `default_ttl` and `max_ttl` Terraform locals alone do **not** configure Coder scheduling.
7. Configure a provider-side prepaid/spend cap or a fixed affordable node pool, disable unwanted autoscaling and auto-recharge where available, and set budget alerts for nodes, persistent disks, snapshots, egress and Coder's database. Namespace ResourceQuota blocks new resources but cannot stop charges for preexisting nodes or cloud disks. Inspect invoice rates before choosing the global cap of five pods.
8. With a separate staging setup, validate Pro one-slot/Team five-slot behavior, simultaneous POSTs, user-to-user deletion isolation, deletion that returns 202 until Coder is gone, retries after an API outage, and a canceled subscription. Confirm the only billable path to a pod runs through the checked route or the guarded Coder templates. Then, and only then, set `BILLABLE_OPERATIONS_ENABLED=true` and `CODER_WORKSPACE_CREATION_ENABLED=true` server-side. Restart/deploy the website, and test a real small pod. Do NOT set these on a public browser or expose `CODER_API_TOKEN` or the Supabase service-role key.

## Failure / emergency stop

- Set `CODER_WORKSPACE_CREATION_ENABLED=false` and redeploy. This stops *new website launches*, not existing pods, direct Coder actions or storage charges. Separately suspend Coder template create permissions, stop (do not delete) running workspaces after warning users, and preserve PVCs until data is backed up. Use provider controls for node/disk/spend shutdown.
- For a slot in `reserved` state after a timeout, inspect the shared Coder owner's workspace list by **name** and check the real pod/PVC. If created, attach the correct Coder UUID to that user's slot after verifying ownership; if absent, confirm no active Coder build or residual PVC before any privileged manual release. Do not put a timed expiry on reservations.
- For a slot in `deleting` state, the management page can recheck deletion. A 202 response means NOT deleted yet; never release on 202 or on a Coder API timeout. A true 404 is required. Even after 404, inspect orphan PVCs and snapshot retention in the cluster.
- Plan limits are maximum allocated workspaces, **not runtime-hour billing or a guaranteed dollar ceiling**. New Kubernetes nodes and long-running existing pods still cost money, and image/3D jobs outside this namespace remain a separate cost exposure.
